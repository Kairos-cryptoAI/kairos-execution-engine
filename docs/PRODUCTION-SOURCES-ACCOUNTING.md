# Production transport, source truth and terminal accounting

This is an explicit engineering continuation of
[the lifecycle composition](PRODUCTION-LIFECYCLE.md), not a deployed trading
service, a qualified account, an owner arm or a readiness promotion. Default
settings and factories still refuse LIVE. Strategy and frozen evidence are
unchanged.

## Actual SDK transport, not another signer

`ProductionEvedexTransport.from_deployment` constructs the additive
`ProductionEvedexSdkClient` and PROD-only Node entrypoint. It does not start a
process or read a key. Explicit preflight validates the reviewed Node 22 runtime
before the API-key-only SDK client can authenticate the exact exchange account.
No wallet key, wallet login, new credential, delegated signature or fallback
signer is created.

The transport uses SDK 1.2.11 / exchange-api 1.0.70 / exchange-crypto 1.1.0,
official PROD origins and the installed SDK's chain 42161. Custody must match
that exact chain, reviewed managed schema and account. The runtime independently
compares the complete custody binding with its actual sender, including for
TP/SL whose REST body contains no chainId. A historical/synthetic 161803 binding
is rejected, not rewritten or treated as venue acceptance.

Five pre-signed POST operations go through the existing SDK API methods with
unchanged decimal strings, parent metadata and signatures. Signing and Risk
remain upstream behind the existing durable one-use claims. There is no generic
POST/DELETE route, transfer, withdrawal, leverage-setting operation or mutation
retry. A cancellation DELETE is not promoted to CANCELED without a subsequent
positive read of that exact cancelled order/protection. A fill race, missing
record or unknown response remains unresolved. Process/protocol failures latch
the client; a failed process is not silently restarted or adopted.

The pinned SDK Gateway uses its own supported RestClient extension with fixed
HTTPS origins/methods checked before an API-key header is attached. HTTP has no
redirect or environment-proxy following, a 20-second timeout and 4 MiB HTTP bounds;
JWT/refresh sessions and arbitrary endpoints are refused. SDK diagnostics are
replaced with fixed public errors, never request/response headers or key text.
The IPC response frame allows a fixed 4 KiB envelope above that bound; an
oversized serialized reply remains an unresolved outcome, never a retry. No
global Axios defaults or interceptors are changed.

## What the actual account/history API does and does not establish

`ProductionHistoryCollector` calls the same transport's typed account identity,
order history, TP/SL history and funding-balance methods. It retains ordered
retrieval times, query JSON, canonical parsed SDK replies and hashes; decimal
strings are not converted to float. Account mismatch, count drift, repeated
IDs/cursors, size/time/page overflow and transport errors refuse the capture.
Exhausting pagination is not proof of immutable cross-page membership.

These are **parsed SDK replies**, not original HTTP bytes. JavaScript Number
decoding may already have rounded numeric fields. The fixed source assessment
does not invent a completeness bit, a global sequence, a missing fee or a zero
funding payment. `PinnedEvedexTerminalEvidenceVerifier` can be registered in the
existing reconciler, but deliberately refuses terminal/accounting authority for
this source. The corresponding guard refuses `ExposureSnapshotV1` publication.

Concrete missing guarantees in the installed primary SDK/API declarations:

- No account-wide atomic snapshot or shared revision across components.
- Offset/next order pagination has no immutable snapshot/time-range contract.
- `getFunding` returns coin balances, not a complete funding-payment ledger.
- TP/SL records do not expose the original entry parent; triggerOrder names an
  exit generated by the trigger, not the parent entry.
- Order fills are nonrecoverable in the pinned WS gateway; callbacks discard
  publication positions. A local buffer sequence is not an exchange sequence.

The public primary API declarations and endpoints are documented in
[official exchange-api types](https://github.com/evedex-official/exchange-api/blob/master/src/utils/types.ts)
and [REST gateway](https://github.com/evedex-official/exchange-api/blob/master/src/exchangeRestGateway.ts).
Mutable master is explanatory, not a replacement for the exact installed
package/source hashes recorded in the dated meta-repository receipt.

The existing shipped Risk producer is also PAPER/DEV-only: RiskSettings refuses
LIVE, PaperRiskPipeline accepts DEV measurements and constructs PAPER decisions,
and the runtime consumes PAPER recovery/account records. The existing Core
LIVE DTO and exact geometry binding are not an authenticated LIVE producer.
This work does not relabel PAPER approval, copy an approved boolean into an
independent Risk record, or generate account economics from these unqualified
captures. Real entry approval therefore remains blocked.

## Explicit fresh v3 accounting after accepted reconciliation

Default state-v2 and receipt-v1 behaviour is preserved. No migration of retained
state, reservation deletion, queue reset or primary database change is included.
The opt-in path uses fresh state schema version 3, separately provisioned
reconciliation schema version 2 and a separate accounting schema/role.

Receipt-v2 additionally binds position side, complete signed funding cost,
settlement time, exact owner-arm/request identity and zero unowned exposure.
`PostgresProductionAccounting.accept_terminal_receipt` rechecks canonical body,
all SQL projections, exact account/context/database/arm/request/effect/trade
lineage, freshness, complete fills and zero residuals. The append is protected
by two foreign keys, immutable records and the same account advisory lock used
by reservation admission. The accounting writer cannot alter Risk, owner arms
or terminal history; runtime cannot append releases.

The lifecycle's `reconcile_closed_account(..., accounting=...)` first obtains
the independent terminal receipt, then passes its exact UUID/hash to this
acceptor. Wrong versions or scopes refuse before reconciliation; an accounting
failure retains the receipt and does not report a release. Without the explicit
accounting argument, the historical no-release path remains unchanged.

Freshness is checked at the original database-stamped receipt insertion, not
at every later accounting attempt. An outage cannot make an otherwise accepted
immutable receipt expire before its first accounting append. Exact receipt-v2
replay retains the original identity; refreshed or conflicting evidence cannot
replace it. First-time stale evidence still fails, and the caller cannot
backdate the database insertion timestamp.

Only an accepted row removes that exact reservation from open risk/notional.
The original reservation remains permanently recorded. Exact net accounting is
gross PnL minus fees minus signed funding cost (positive means debit). Entry
admission conservatively retains `max(0,-gross) + fees + max(0,funding debit)`;
profits never replenish loss capacity. Historical cap/equity/baseline floors
remain; there is no automatic UTC-day reset, new arm reset or loss forgiveness.
An overlap with an authoritative reported loss can over-count conservatively;
normal daily reset requires a separately qualified account ledger.

## Proof boundary and actual remaining dependency

Unit and native PostgreSQL tests use explicitly synthetic authority/history.
They exercise SQL roles, FK/immutability, complete-vs-unknown funding, conflicting
payloads, replay, concurrent accounting/reservations and retained loss floors.
SDK tests exercise the pinned wire/client boundary offline. None is evidence
of actual EVEDEX orders, fills, account continuity or profitable trading.

To close the real PROD path, an accepted venue source/contract must establish
coherent account state, complete settlement/fees/funding and exact protection
lineage, followed by an independently authenticated current LIVE Risk producer
on those facts and the accepted custody/owner deployment. Merely adding a key,
repeating GETs or weakening the verifier cannot supply those guarantees. No real
request or trade is needed to demonstrate that missing source contract.
